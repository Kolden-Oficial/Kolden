### Rebrand NutriOS Pro v2 — tokens 8 cores dual-mode (2026-07-03)

Quando a paleta ganha um subsistema warm coerente (Linen Cream + Warm Linen + Terracotta + Espresso), o light deixa de ser variante do dark e vira seu próprio tema de referência com identidade. Regra de projeto: se a marca escolhe DUAS temperaturas cromáticas fortes (verde-frio + linho-quente), documente as duas como canônicas com pares de contraste próprios, não como "modo A e derivado de A" | 2026-07-03
- Substituição de cor removida em token semântico exige explicitar a heurística de derivação, não só o hex novo. Ex.: Forest Green `#0A5C52` deixou de existir mas era `--border`. Escolhi "Dark Teal +8% lightness = hsl(170 53% 23%)" e DOCUMENTEI a fórmula no `$description` do JSON. Isso permite regenerar o valor se Dark Teal mudar no futuro, sem quebrar a intenção do border | 2026-07-03
- Fonte proprietária "All Rights Reserved" (não SIL OFL) precisa de política dupla no leia-me: (a) uso interno em documentos versionados no repositório privado OK via @font-face local; (b) produção pública exige webfont license CONFIRMADA com o autor OU wordmark como SVG/PNG estático. Metadata name table do OTF (via fontTools) é a fonte de verdade da licença — sempre extrair antes de assumir o que a fonte permite | 2026-07-03
- Cálculo WCAG 2.1 manual sobre 8 cores rende insight que a tabela do brandbook não mostra sozinha: pares "de mesmo lado" (mint sobre linen 1.33:1, terracotta sobre linen 2.52:1, aqua sobre linen 2.05:1) falham como TEXTO — no light-mode qualquer accent vibrante vira FILL, nunca texto. O texto no light é sempre Espresso sobre linen/warm-linen. Documentar isso como regra prática (§5.3) evita bug futuro de "por que meu botão-primário verde soma contraste ruim" | 2026-07-03
- Introduzir token NOVO (`--accent-warm`) num contrato shadcn/ui já estabelecido é seguro porque shadcn é opt-in por classe — componentes que não referenciam o token não quebram. Regra: sempre adicionar como sufixo semântico (`-warm`, `-cool`, `-brand`) para não colidir com o namespace shadcn nativo (`--accent` cru) | 2026-07-03

### Vetorização de monograma Omiron (Direção 1 — Aglaia) (2026-07-07)
- Modulação de espessura Didone REAL (não simulada com `stroke-width` uniforme) resolve com DOIS ELIPSES concêntricos `fill="currentColor"` + `fill-rule="evenodd"`. Contra-forma criada pela diferença entre elipses de rx/ry distintos gera as hairlines finas no topo/base e hastes grossas nas laterais AUTOMATICAMENTE — matemática do path faz o desenho. Ex.: hero externa (rx=75, ry=65) − interna (rx=60, ry=52) → laterais 15 uni de espessura, topo/base 13 uni. Contraste axial ≈ 1.15:1. Para 40px, atenuar (hero rx=76,ry=66 vs interna rx=60,ry=48) — engrossa hairlines 15% sem quebrar identidade Didone | 2026-07-07
- GOTCHA `currentColor` em SVG externo referenciado via `<img src=".svg">` NÃO herda `color` do container HTML — o SVG root resolve `currentColor` como preto default. Só funciona quando: (a) SVG inline direto no HTML, ou (b) `<symbol>` num sprite consumido via `<svg><use href="#id"/></svg>` inline. Regra de projeto: sempre que um showcase/preview precisa provar "cor herdada por token do container", montar SPRITE INLINE com `<symbol id>` + `<use>`. Salvei essa lição pagando com um refactor completo do showcase que já estava com 250 linhas | 2026-07-07
- GOTCHA XML strict — comentários `<!--` NÃO podem conter `--` (dois hífens consecutivos), regra XML 1.0. Meu separador estético `<!-- ============ -->` estava usando `--------` e todos os 5 SVGs falhavam `ET.parse()`. Browsers modernos aceitam permissivamente, mas parsers strict (build tools, otimizadores SVG, validação CI) rejeitam. Regra: usar `====` ou `~~~~` em separadores dentro de comentário. Validar com `xml.etree.ElementTree` antes de fechar entrega de SVG | 2026-07-07
- Consumidor `<svg viewBox>` do símbolo do sprite PRECISA casar com o viewBox do `<symbol>` interno, senão só uma fração do símbolo renderiza. Quando substituí `<symbol id="omiron-mark" viewBox="0 0 40 40">` por `viewBox="0 0 200 200"` no sprite do brandbook, tive de trocar TODOS os `<svg viewBox="0 0 40 40"><use href="#omiron-mark"/></svg>` para `viewBox="0 0 200 200"` no consumo. Sem isso, o `<use>` puxa o symbol de 200×200 mas o SVG root recorta em 40×40, mostrando só o canto superior esquerdo | 2026-07-07
- CSS `mask-image: url(.svg)` para plantar um símbolo em N contextos SEM editar N vezes (ex.: selo do monograma no canto inferior direito de 14 slides) é elegante mas tem gotcha: máscara usa APENAS o alpha channel do SVG, ignora `fill`/`currentColor` interno. A cor do resultado vem do `background: currentColor` (ou hex) do elemento com a máscara. Regra: para máscara, SVG interno pode ter `fill="black"` ou `fill="currentColor"` — não importa, a máscara só lê alpha. Combinar com `background: currentColor` no `::after` faz o selo herdar cor do container via CSS. Prefixar com `-webkit-mask-*` para Chrome/Safari | 2026-07-07
- Serifa dupla como assinatura autoral resolvida em BRACKET (não voluta): 4 retângulos por serifa (2 hastes verticais finíssimas + 2 brackets horizontais no final). Largura 1.6 uni no hero (sobrevive à escala 200-800px), ausente na versão 40 (empasta abaixo de 60px). Regra: assinatura autoral que só sobrevive em escala grande vive por ARQUIVO separado, não por CSS conditional — dá controle explícito ao consumidor | 2026-07-07
- Entrelaçamento OM geométrico: as hastes externas do M coincidem exatamente com as bordas internas do O (rx interno = 60, borda esquerda x=40, borda direita x=160). Hastes do M em x=[39,47] e x=[153,161] — o M "nasce" da parede interna do O. Sem esse casamento geométrico, o M vira glifo independente ao lado do O e o entrelaçamento fica retórico | 2026-07-07
- `<text>` dentro de `<symbol>` SVG herda o `fill="currentColor"` do wrapper (garantido no lockup vertical/horizontal). `font-family` do `<text>` aceita fallback stack — usei `"'EB Garamond', 'Cormorant Garamond', 'Georgia', serif"` para degradar com elegância se a web font não carregar em contexto offline/CDN bloqueada | 2026-07-07
